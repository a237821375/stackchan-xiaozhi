随后用户确认 USB 已移回底座、开关 ON。底座连接下反馈保持有效，临时 `head arm` 后自动动作仍关闭。先后执行两轴各 +2° 探测及回正：yaw 反馈从 −17.50° 变为 −16.56°，pitch 从 12.50° 变为 13.44°；探测目标分别为 −15.50°、14.50°，不能把命令增量写成实际完整移动 2°。回正目标 (0,10)，停止反馈约 (−0.94,10.31)，均处于当前完成容差内。整个过程无反馈故障、UART 错帧或读写失败。机械方向、正面姿态及是否异响仍待用户确认；当前保持 `approved=false`、`automatic=false`，尚未启用摸头、待机张望或跳舞。小幅探测不等于完整机械范围和功能验收。

此前运动验收曾被通信故障阻断：两轴尚未启用、运动写入次数均为 0 时，已出现 UART 错帧和反馈读取失败，随后锁定为 `communication_timeout`；拨底座开关并拔 USB 后仍有异常。旧自定义 2.5.0 同样禁用运动的 60.074 秒只读对照中，两轴分别读取 2906/2933 次，失败 68/92 次，运动写入均为 0，说明故障并非仅新版出现。没有批准动作或启用探测、摸头、跳舞来绕过此故障。此时既不能判定新版运动功能通过，也不能仅凭错帧断定电机或硬件损坏。

完整断电复测也未消除错帧：按[官方开关机说明](https://docs.m5stack.com/en/StackChan)，长按侧面 USB-C 旁的电源键约 6 秒，用户确认屏幕完全熄灭后重新开机。旧自定义 2.5.0 在启动稳定后的 60.142 秒窗口，两轴分别读取 3004/3001 次，失败 12/7 次，UART 新增 16 次错帧，运动写入仍为 0。此窗口反馈大多有效、未锁定故障，但不能据此宣称通信完全恢复。新版在同样完整关机条件下的只读复测尚未完成。

RST 不等于关机；底座开关 OFF 和拔 USB 不能单独证明整机已断电。只读对照暂时关闭了旧版 `head_ctl/verified`；新版校准记录也保持未批准。只读阶段不执行自动张望、摸头动作或 AI 运动指令。

前一轮尝试切回保护版时，完整备份读取到约 13MiB 发生 USB 瞬断（`Device not configured`）。macOS 内核记录连接丢失后约半秒重新枚举，用户确认未操作按键或插拔。程序在保存完整备份和任何写入之前停止，没有使用部分备份继续安装，当时仍为自定义 2.5.0、动作未批准。后续头部 USB 的成功不能抹去此失败记录，也不能证明底座接口损坏或长期可靠；不能将前一次失败误报为烧录完成。

主机模拟与编译不能确定舵机总线长期可靠、机械范围安全或其他屏幕版本兼容。2026-10-01 的短时复测在[归档记录](stackchan-history/MOTION-20261001.md)，不等于本版通过以下清单。

### 小幅探测的限制（2026-10-07）

用户未观察清楚首轮动作，因此没有取得人工确认或批准。再次从回正姿态发出 +2° yaw 探测，实际 yaw 从 −0.94° 变为 0.62°；随后 +2° pitch 探测目标为 12°，实际 pitch 保持 10.31°，不能报告为抬头成功。此时读写与 UART 统计仍零失败，未报过载或卡滞，原因未确认。追加抬头探测被自动审批拒绝，未执行；已发送停止并确认停止姿态，自动动作与批准标志仍关闭。

当前 `kSettleToleranceDegrees=2.5°`，大于探测命令 2°，所以 `completed` 不能单独证明小幅探测实际运动。该数值引用原厂堵转检查排除小误差的阈值，不能据此认定它适合作为探测验收阈值。原厂 `ScsServo::is_moving_impl()` 读取 `ReadMove`，当前 `FactoryAxis` 未覆盖该方法；原厂动画代码的复用不等于整个反馈和完成判断流程一致。需要对照控制链及实际目标写入，不能把未变化的角度直接归因为电机损坏。

用户明确确认现场观察后，临时启用本地动作，依次执行一次 yaw +2°、一次 pitch +2° 和回正。yaw 从 1.88° 变为 2.81°，目标 3.88°；pitch 从 10.31° 变为 11.56°，目标 12.31°。两次 `pose_command_motion_observed=true`、`pose_command_finished=true`、`pose_command_target_reached=false`，停止状态正确显示 `target_not_reached`。只读诊断读取到两轴存储目标分别为 473、649，实际反馈分别为 470、647；目标确实已写入，未到位的原因仍待确认。回正目标 (0,10)，停止时实际约 (0.94,10.31)，同样报告未到位。之后发送停止保持当前姿态，不继续加幅或重复抬头。

用户授权继续现场测试，诊断应用反馈有效、无故障。临时本地启用后，执行一次 `head right`（yaw=10°、pitch=10°）和一次 `head center`，随后停止；没有批准自动动作、连续重试或修改舵机参数。yaw 从约 0.31° 到 9.38°，目标寄存器 493、实际 491；回正目标寄存器 461、实际 464（约 0.94°），pitch 实际约 10.31°。新完成诊断均为已运动、已停止、未精确到位。

### 源码对照结论（2026-10-07）

按用户要求停止重复动作测试，重新下载当前原厂 `hal_servo.cpp`、`motion/servo.cpp` 和 `app_avatar.cpp`，与此前缓存逐字节比较，未发现变化。对照原厂[堵转判断](https://github.com/m5stack/StackChan/blob/1b5765599fba8aaad1811d9a79358ccc7051f5f3/firmware/main/hal/hal_servo.cpp)和[动画完成逻辑](https://github.com/m5stack/StackChan/blob/1b5765599fba8aaad1811d9a79358ccc7051f5f3/firmware/main/stackchan/motion/servo.cpp)，得到以下相互独立的结论：

- 当前 AI 指令拒绝有明确的软件原因：`RemoteMotionAllowed` 要求 `approved && armed`；本机校准 `verified=0` 会返回 `local head movement verification required`，自动动作也保持关闭。此验收状态是本项目引入的，不能将该拒绝归因为电机损坏或把“未批准”伪称“电机卡住”。
- 新增的一反馈计数（约 0.3125°）到位条件是本项目诊断标准，未得到原厂机械精度保证。实测能转动但差 2～3 个计数时显示未到位；该状态本身不锁定故障，也不阻止下一条动作，不能把它当作 AI 拒绝动作的原因。
- 自定义 `AxisStall` 只按位置 1.2 秒无进展判断；原厂还结合电流/负载绝对值或上升值、方向与连续样本。主机调用真实 `AxisStall` 复现了“目标误差较大、位置 1301 ms 不变即返回堵转”，其接口没有电流/负载输入，因此无法区分低负载未动与有负载堵转。该差异是误报风险，尚不能证明每一次历史锁定均由它触发。
- 原厂以弹簧动画和舵机移动标志判断是否仍在运动，并对高频 App 指令切换角度自动同步；没有采用本项目的一计数精确到位标准。继承原厂轨迹不等于全部控制与保护逻辑一致。

上述三项软件行为已用实际头文件的主机复现（ASan/UBSan）核对，本轮未执行额外机器人运动、改 EEPROM、放宽保护或解除未批准状态。历史 UART 错帧及通信超时仍属另一个未解决问题，不能由本轮源码结论抹去。

### 停止状态与堵转证据修复（2026-10-07，实机待验证）

源码对照后修改：静止统一报告 `stopped`，严格编码器对齐仅保留为诊断字段，增加实际残余误差和未批准原因；不以微小误差判定故障。保留原有 1.2 秒无进展停止，改报告 `motion_no_progress`；原厂 50 ms/8 计数排除/1 计数进展/电流与负载证据/两次确认用于分类 `mechanical_stall`。堵转证据比较最近一次成功写入的弹簧步目标，不能提前与最终远端目标比较；新命令不重置原连续无进展计时。范围、过载阈值、通信保护与本机人工批准策略未改。

主机真实 FactoryAxis 慢速 0→5°、speed=400、60/120/180 ms 负载 0/150/300 的回归显示：用最终目标提前检查会误报，而用已下发步目标不会；另覆盖低负载不报堵转、负载/电流上升、采样间隔、方向改变、Reset 和写失败。静止残余 0.625° 的状态测试在旧代码失败，修复后通过。12 个 C++ 测试程序（ASan/UBSan）及 K151/ESP-IDF 6.0.1 编译通过，云端覆盖保护开启；应用 SHA256 为 `5ecd0439172d23fda0e79e4f3a3ad6669e2b638c3b362c2c481facaf214d2d51`。源码版本 `18a6e77`。首次安装尝试时 USB 串口不存在，在备份和任何写入前停止，修复应用尚未安装。本节不代表实机已恢复或真实堵转已经验证；禁止人为堵住头部制造测试。

## 分阶段验证

- [ ] 连网后保持本项目版本，云端自动或远程升级不能覆盖应用；小智激活和服务连接正常。

- [ ] 每台设备按校准指南验证缺失配置禁用、保存重启、只读反馈、小幅两轴探测、验收启用。修改配置后旧验收不能继续使用，撤销后重启不恢复已批准状态。
- [ ] 确认原厂风格表情正常，普通待机嘴不动，讲话按各情绪动嘴，困困一直闭嘴；对话字幕隐藏，状态界面可读。
- [ ] 连续待机 30～60 分钟，记录两轴反馈读取/写入总数、失败数、UART 帧错误与故障次数。
- [ ] 待机张望不同阶段摸头，至少重复 20 次：中断张望、柔和抬头、持续轻点头、松手约 3 秒恢复；之后仍能回正与执行明确指令。
- [ ] 连续对话、点头、摇头、回正及停止/恢复，检查抢占、幅度、结束位置和自动动作是否符合指令。
- [ ] 多次 15 秒跳舞，观察 RGB 闪烁，结束及中断均恢复规定姿态并关灯；分别验证摸头、停止跳舞和新姿态指令的中断。
- [ ] 检查短按 RST 与完整断电再启动后的配置、绑定和动作状态区别。
- [ ] 出现自然通信故障时，验证其报告为通信异常并有限恢复；超时锁定后不反复自动重启动作。无效反馈不转成角度，不把通信异常说成机械卡死。

不要人为堵转、掰头、带电拔插内部总线来制造故障。头部出现异常时先停止，不通过增大保护阈值或连发 resume 掩盖问题。

## 日志与结论

保留经过隐私筛选的 `head status`、`UART_STATS`、`SERVO_STATS` 和故障原因，报告动作次数、统计窗口、分母与错误数。灯光关闭日志只证明指令确认，还需肉眼确认灯灭。

测试失败先保存现场，区分 `communication_timeout`、`mechanical_stall`、`overload`、`servo_alarm` 和配置异常。相同源码、供电、环境下做对照，不能凭单次重启恢复判定根因已解决。当前舵机偶发错码根因未确认；本次仓库修复没有修改运动速度、保护阈值或声称硬件通信问题已根除。
